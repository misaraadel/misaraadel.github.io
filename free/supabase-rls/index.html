الداتابيز بتاعتك مفتوحة؟ 🔓 شغّل RLS على Supabase صح

من ريل «غلطات مواقع الـAI #٥: الداتابيز بتاعتك مفتوحة» على إنستجرام:

👉 instagram.com/misarahamed.webdeveloper

مواقع كتير بتتعمل بالـAI (Lovable وBolt وCursor…) وبتستخدم Supabase. الموقع بيكلّم الداتابيز من المتصفح على طول بمفتاح اسمه anon key، والمفتاح ده عادي إنه يبقى باين. الحماية الحقيقية هي RLS (Row Level Security).

لو الـRLS مقفول على أي جدول، يبقى أي حد معاه لينك المشروع والمفتاح، وهما الاتنين باينين في F12، يقدر يقرا ويعدّل ويمسح كل الصفوف اللي في الجدول ده.

🧪 اختبر موقعك في دقيقة (موقعك إنت بس)

  1. افتح Supabase ← Table Editor: أي جدول جنب اسمه RLS disabled أو علامة ⚠️ يبقى مفتوح.
  2. أو من Advisors ← Security Advisor: هيطلعلك تحذير «RLS Disabled in Public» لكل جدول مفتوح.
  3. أو جرّب من الكونسول في موقعك (وإنت مش عامل تسجيل دخول):
const { data, error } = await supabase.from('users').select('*');
console.log(data?.length, error);

لو رجعلك صفوف وإنت مش مسجّل دخول، يبقى الجدول مفتوح.

⚠️ جرّب على مشروعك إنت بس. إنك تسحب داتا من موقع حد تاني من غير إذنه حاجة مش قانونية.

🔒 الحل: شغّل RLS وحط Policy

١) شغّل RLS على كل جدول (من Table Editor ← Enable RLS، أو بـSQL):

alter table public.users enable row level security;

بعد الخطوة دي محدش هيقدر يقرا حاجة خالص لحد ما تحط Policies، وده الطبيعي.

٢) Policy: كل يوزر يشوف ويعدّل الصف بتاعه بس:

create policy "read own profile" on public.users
  for select using ( auth.uid() = id );

create policy "update own profile" on public.users
  for update using ( auth.uid() = id );

٣) جدول عام (زي المنتجات) أي حد يقراه، بس محدش يعدّله من المتصفح:

alter table public.products enable row level security;

create policy "anyone can read products" on public.products
  for select using ( true );

(من غير Policy للـinsert والـupdate والـdelete، التعديل هيبقى ممنوع من المتصفح.)

٤) الطلبات (orders): كل يوزر يشوف طلباته ويضيف طلب باسمه بس:

alter table public.orders enable row level security;

create policy "own orders" on public.orders
  for select using ( auth.uid() = user_id );

create policy "create own order" on public.orders
  for insert with check ( auth.uid() = user_id );

❌ غلطات تانية لازم تاخد بالك منها

  • service_role key ماينفعش يتحط في كود المتصفح أبدًا، لإنه بيعدّي الـRLS كله. مكانه السيرفر بس (Edge Function أو API route).
  • Storage buckets ليها Policies لوحدها. اتأكد إن الـbucket مش Public لو فيه ملفات خاصة.
  • Views وFunctions: الـview ممكن تعدّي الـRLS. استخدم security_invoker = on في الـviews.
  • بعد ما تضيف أي جدول جديد، ارجع لـ Security Advisor تاني.

🤖 برومبت تدّيه للـAI (Lovable / Cursor / Bolt)

راجع مشروع Supabase ده من ناحية الأمان:
- طلّعلي كل جدول الـRLS فيه مقفول، واكتب SQL يشغّله.
- اكتب Policies لكل جدول: اليوزر يشوف ويعدّل الصفوف بتاعته بس (auth.uid() = user_id)، والجداول العامة قراءة بس.
- اتأكد إن service_role key مش موجود في أي كود بيروح للمتصفح.
- راجع الـStorage buckets والـviews.
- اكتبلي الـSQL كامل في ملف migration واحد، واشرحلي كل Policy في سطر.
